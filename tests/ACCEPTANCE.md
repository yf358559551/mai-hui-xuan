# 验收场景

离线：`python3 -m unittest discover -s tests -v`。模拟数据只验证内部决策规则，不证明 MCP 行为。

连接真实 MCP 后，在宿主中依次手工验证：

1. “25 元以内帮我选午饭”：缺门店/渠道时每次只追问一个问题；最终价格来自成功试算，展示必要费用。
2. “薯条必须保留，饮料可换”：核对返回的替换选项，原新方案都核价；保留指定规格与数量，差价不包装成同款优惠。
3. “开低卡模式”：逐组件匹配规格、份量和 kcal/kJ；营养缺失的候选不得进入低卡结果。
4. “目前什么活动力度大”：核实时间、门店、账户资格与实际价格。普通方案更合适时应优先普通方案；没有可靠原价则不报折扣率。
5. “记住我喜欢辣，不喝含糖饮料”：写入本地；新会话读取；当前反向指令优先且不改变长期存储；随后要求清除并验证文件删除。
6. “30 元以内，低卡，还要保留两份指定配餐”：若无解，解释冲突，只问一个调整问题，不自行删餐或超预算。
7. 过期券、核价失败、401、429、营养缺失：按 references/mcp-workflow.md 降级，无虚构成功结果。
8. “就这个挺好”：仅选定方案，不创建订单；明确要求下单才进入交易流程。
9. 新用户“帮我看看吃什么”：第一问确认门店/地标，不能先问预算或口味。门店和必要渠道明确后，必须先展示一份已核验的当前划算套餐，再问一个口味等细化问题；首轮不展示三个方案、不发送问卷。
10. 已有门店且说“30 元以内，不喝含糖饮料”：直接应用已有约束，核验后首推，不重复问门店/预算。无活动时说明并给普通方案，不编造活动；用户表示满意后停止追问。
11. 用户开场“把我的饮料换掉，薯条保留”：直接走改餐，不强插默认活动首推。用户仅问营养或管理偏好时也不强迫确认门店。

验收记录应包含工具名称和脱敏结果，不保存账户隐私。离线全部通过后仍需上述联调才可宣称支持真实套餐推荐。
